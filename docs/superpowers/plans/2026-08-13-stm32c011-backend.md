# STM32C011J6M6 Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a fourth Data Vault platform backend, `stm32c011`, targeting the STMicroelectronics STM32C011J6M6 (Cortex-M0+, SO8N 8-pin package) on a bare/hand-wired chip, implementing the same `vault/platform.h` HAL contract the `lpc810`, `stm32u031`, and `efm32g210` backends already satisfy. `core/` is unmodified by this plan.

**Architecture:** Same three-layer pattern as the existing backends: `core/` (unchanged), `platform.h` (unchanged — no new HAL functions needed), and a new `platform/stm32c011` backend using STM32Cube **HAL** (per design decision — matches the STM32U031 backend's abstraction level and, where the peripheral generation is close enough, its actual call patterns, confirmed by reading `platform/stm32u031/src/platform_stm32u031.c` directly rather than reinventing a style).

**Tech Stack:** C11, CMake 3.20+, `arm-none-eabi-gcc -mcpu=cortex-m0plus`, STM32Cube C0 HAL vendored via git submodule.

## Global Constraints

- `VAULT_CONTEXT_SIZE`: 320 bytes, matching all three existing hardware backends (RadioLib's real persisted-state requirement). Trivial against this part's 6 KB SRAM — the tightest RAM budget of any backend so far, but still comfortably sufficient (see the design spec §8 for the 6 KB figure's source).
- `VAULT_I2C_ADDR`: `0x42` (7-bit), unchanged.
- `VAULT_DEFAULT_WAKE_INTERVAL_SEC`: 60, unchanged.
- Package: SO8N, 8 pins total (`VDD`, `VSS`, `NRST`, and 5 GPIOs). No board schematic exists for this target — see the design spec (`docs/superpowers/specs/2026-08-13-stm32c011-backend-design.md`) §2 for the pin-role table. **Exact GPIO pin names (e.g. `PA4` vs. `PA9`) are NOT confirmed** — this plan uses illustrative names flagged for verification against the real vendored device header/datasheet in Task 1, the same discipline this project already applied when the EFM32G210 backend's guessed `I2C0->ROUTE` `LOCATION0` turned out wrong and was caught during implementation.
- `SWDIO` is shared with debug UART TX when `VAULT_LOG_ENABLED` is set — see Task 7. This means a `VAULT_LOG_ENABLED` build cannot be live-debugged over SWD while running.
- Sleep mode: Stop mode (SRAM/register-retentive) — see the design spec §5 for why Standby/Shutdown are rejected (both wipe SRAM, breaking `vault_core`'s resume-in-place assumption).
- RTC clock source: LSI (internal RC), not LSE — this package has no crystal pins. Matches the STM32U031 backend's own eventual LSI choice (that backend tried LSE first and reverted after a real hardware problem — see `platform/stm32u031/src/platform_stm32u031.c`'s `rtc_init()` comment for the full story); here LSI is not a fallback from a failed LSE attempt, it's the only option from the start.
- No git commit includes a "Co-Authored-By" trailer (repo-wide rule).
- Every register/HAL-API detail flagged "verify against reference manual/vendored header" below is a real open question, not decorative caution — this backend has more of these than usual because there is no board schematic and STM32C0 is a different peripheral generation from STM32U0 despite superficial family-name similarity. Confirm each one before flashing, the same discipline every other backend's code comments already apply throughout this codebase.
- **Genuinely load-bearing unknown, flagged here so it isn't missed:** whether STM32C011 has an RTC peripheral at all. ST's STM32C0 line is a cost-reduced part aimed at replacing simple 8-bit MCUs; some ultra-low-cost lines omit RTC/backup-domain hardware entirely to save die area. Task 1 Step 2 checks this **before** any later task assumes an RTC-based wake timer exists. If it turns out this part has no RTC, STOP after Task 1 and escalate — do not silently redesign the wake mechanism (e.g. around IWDG or LPTIM) without discussing the tradeoffs first, since IWDG's reset-only (non-interrupt) wake behavior already ruled out one such alternative for the EFM32G210 backend's EM3 path, and the same class of problem could apply here too.

- [ ] **Step 2: Write the linker script**

```
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 32K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 6K
}

ENTRY(Reset_Handler)

SECTIONS
{
    .isr_vector :
    {
        KEEP(*(.isr_vector))
    } > FLASH

    .text :
    {
        *(.text*)
        *(.rodata*)
        . = ALIGN(4);
    } > FLASH

    _sidata = LOADADDR(.data);

    .data :
    {
        _sdata = .;
        *(.data*)
        _edata = .;
    } > RAM AT> FLASH

    .bss :
    {
        _sbss = .;
        *(.bss*)
        *(COMMON)
        _ebss = .;
    } > RAM

    ._user_heap_stack :
    {
        . = ALIGN(8);
        . = . + 512;
        . = ALIGN(8);
    } > RAM

    _estack = ORIGIN(RAM) + LENGTH(RAM);
}
```

The `._user_heap_stack` reservation is 512 bytes, not the STM32U031 backend's 1024 -- half of this part's entire 6 KB SRAM is already committed to `VAULT_CONTEXT_SIZE`'s 320 bytes plus its own overhead, so keep the stack reservation proportionally smaller. Verify this is still comfortably sufficient once the real call depth (HAL_I2C listen-mode callbacks, HAL_PWREx Stop-mode entry) is known -- revisit if link-time or runtime stack issues appear later.

Confirm flash/RAM values from Step 1 match before using this file as-is.

- [ ] **Step 1: `platform_stm32c011.c`'s GPIO init, mirroring `platform_stm32u031.c`'s pattern**

```c
#include "vault/platform.h"
#include "stm32c0xx_hal.h"

/* Illustrative pin names -- MUST be replaced with the real SO8N pin map
   confirmed in Task 1 Step 2 before this is trustworthy on real
   hardware. Getting this wrong on an 8-pin part risks shorting two
   signals together, unlike a wrong guess on a 32+ pin part which is
   merely "doesn't work" -- treat this substitution as a hard
   prerequisite, not a nice-to-have. */
#define MAIN_RAIL_EN_PORT GPIOA
#define MAIN_RAIL_EN_PIN  GPIO_PIN_4
#define I2C_SDA_PORT      GPIOA
#define I2C_SDA_PIN       GPIO_PIN_10
#define I2C_SCL_PORT      GPIOA
#define I2C_SCL_PIN       GPIO_PIN_9

static void gpio_init(void) {
    __HAL_RCC_GPIOA_CLK_ENABLE();

    GPIO_InitTypeDef gpio_init = {0};
    gpio_init.Pin = MAIN_RAIL_EN_PIN;
    gpio_init.Mode = GPIO_MODE_OUTPUT_PP;
    gpio_init.Pull = GPIO_NOPULL;
    HAL_GPIO_Init(MAIN_RAIL_EN_PORT, &gpio_init);
    HAL_GPIO_WritePin(MAIN_RAIL_EN_PORT, MAIN_RAIL_EN_PIN, GPIO_PIN_RESET);
}

void platform_main_rail_enable(bool on) {
    HAL_GPIO_WritePin(MAIN_RAIL_EN_PORT, MAIN_RAIL_EN_PIN,
                       on ? GPIO_PIN_SET : GPIO_PIN_RESET);
}

void platform_bus_isolate(void) {
    /* Analog, no pull -- same parasitic-back-powering mitigation every
       other backend's platform_bus_isolate() already applies (design
       spec, MCU_Analysis_Report.md section 5). */
    GPIO_InitTypeDef gpio_init = {0};
    gpio_init.Pin = I2C_SDA_PIN | I2C_SCL_PIN;
    gpio_init.Mode = GPIO_MODE_ANALOG;
    gpio_init.Pull = GPIO_NOPULL;
    HAL_GPIO_Init(I2C_SDA_PORT, &gpio_init);
}

void platform_init(void) {
    HAL_Init();
    gpio_init();
    /* Task 4 (clock/RTC) and Task 7 (debug UART) append their own init
       calls here -- do not add speculative calls to functions that
       don't exist yet. */
}
```

- [ ] **Step 2: RTC init, mirroring `platform_stm32u031.c`'s `rtc_init()` pattern but LSI-only from the start**

```c
#include "stm32c0xx_hal.h"

static RTC_HandleTypeDef s_rtc_handle;

static void rtc_init(void) {
    /* LSI only -- this package has no crystal pins (design spec section
       5), so LSE was never a candidate here the way it briefly was for
       STM32U031. Confirm HAL_PWR_EnableBkUpAccess() is still the correct
       call on this family before the RTC/backup-domain registers can be
       written -- verify against the STM32C0 reference manual's "Backup
       domain" section; do not assume it's identical to STM32U031's just
       because both are ST parts. */
    HAL_PWR_EnableBkUpAccess();

    RCC_OscInitTypeDef lsi_osc_init = {0};
    lsi_osc_init.OscillatorType = RCC_OSCILLATORTYPE_LSI;
    lsi_osc_init.LSIState = RCC_LSI_ON;
    HAL_RCC_OscConfig(&lsi_osc_init);

    RCC_PeriphCLKInitTypeDef periph_clk_init = {0};
    periph_clk_init.PeriphClockSelection = RCC_PERIPHCLK_RTC;
    periph_clk_init.RTCClockSelection = RCC_RTCCLKSOURCE_LSI;
    HAL_RCCEx_PeriphCLKConfig(&periph_clk_init);

    __HAL_RCC_RTC_ENABLE();
    s_rtc_handle.Instance = RTC;
    s_rtc_handle.Init.HourFormat = RTC_HOURFORMAT_24;
    /* AsynchPrediv/SynchPrediv values below assume a real 32.768 kHz
       RTCCLK, matching STM32U031's own LSE-targeted values -- but LSI's
       actual frequency on STM32C0 is a DIFFERENT nominal value than
       STM32U031's LSI (verify against the STM32C011 datasheet's "LSI
       oscillator characteristics" table, do not assume ~32 kHz), and
       carries a much wider tolerance than a crystal regardless. Recompute
       these two prediv values from the real LSI nominal frequency before
       trusting platform_wakeup_timer_arm() below to mean what it says in
       seconds. */
    s_rtc_handle.Init.AsynchPrediv = 127;
    s_rtc_handle.Init.SynchPrediv = 255;
```
